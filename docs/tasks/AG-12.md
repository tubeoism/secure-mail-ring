## Goal
A small Cloudflare Worker on the free tier receives the once-a-day heartbeat of the add-in (`{ h, bundle, manifest }`: a salted hash of the mailbox and two version strings), stores one row per hash, and gives the owner a protected report of how many distinct users were seen and on which versions. It stores and logs nothing else.

## Allowed paths
- `worker/heartbeat/**` (source, tests, `schema.sql`, `wrangler.toml`, `README.md`)

## Inputs (read-only)
- `@smr/core`: `parseHeartbeat` (validates the body with the strict schema; unknown fields are rejected), type `HeartbeatPayload`. Import nothing else from the core.
- The record contract: `h` is 64 lowercase hex characters, `bundle` and `manifest` are dotted numbers with an optional short `+build` tag. See `packages/core/src/heartbeat.ts`.
- Plan D-17 and NFR-3: the Worker never receives content, recipients, file names or ring data, and must not keep anything that identifies a device or a network (IP address, user agent, headers).

## Requirements
1. **Handler.** A pure function `handleRequest(request, env, store)` returning a `Response`, with `export default { fetch }` wiring it to Cloudflare. All logic is testable on Node with a fake `store`; the Worker needs no new npm dependency (declare the few Worker and D1 types you use in a local `types.ts`; do not add `@cloudflare/workers-types` or `wrangler` to the repository, the owner runs `npx wrangler` at deploy time).
2. **`POST /v1/hb`.** Body must be JSON, at most 256 bytes (reject earlier by `Content-Length` and by reading no more than 257 bytes), and valid for `parseHeartbeat`. Answers: `204` with no body on success; `400` invalid; `405` other method; `413` too large; `415` wrong content type; `403` origin not allowed; `404` other paths. Error bodies are fixed short strings that never echo input.
3. **CORS.** `env.ALLOWED_ORIGIN` (set at deploy, not in the repository) is the only origin allowed. Answer the `OPTIONS` preflight for `POST` with `Content-Type`, `Access-Control-Max-Age` of one day, and no credentials. A request with another or a missing `Origin` header gets `403` and nothing is stored. If `ALLOWED_ORIGIN` is unset, every request gets `403`.
4. **Storage (D1).** Table `seen(h TEXT PRIMARY KEY, bundle TEXT NOT NULL, manifest TEXT NOT NULL, first_seen TEXT NOT NULL, last_seen TEXT NOT NULL)` in `schema.sql`. On success upsert by `h`: keep `first_seen`, set `bundle`, `manifest` and `last_seen` to the current UTC date (`YYYY-MM-DD`, from the Worker clock, never from the client). One write per request.
5. **Privacy.** Do not read, store or log the client IP, `User-Agent`, `Referer`, cookies or any header except `Origin`, `Content-Type` and `Content-Length`. No `console.*` calls. No request body is kept except the three validated fields.
6. **`GET /v1/report`.** Requires `Authorization: Bearer <token>` equal to `env.REPORT_TOKEN` (compared in constant time; unset token means `403`). Query `days` (default 7, 1 to 365). Returns JSON: `{ asOf, days, distinctSeen, byBundle: { "<version>": n }, byManifest: { "<version>": n } }` counted over rows with `last_seen` within the window. With `?hashes=1` it also returns `hashes: [...]` for matching against the hashed target list offline. Never returns anything else.
7. **Runbook.** `README.md` in English: create the D1 database, apply `schema.sql`, set `ALLOWED_ORIGIN` and the `REPORT_TOKEN` secret, deploy, test with `curl`. `wrangler.toml` holds placeholders only: no account id, database id, domain or token.
8. Everything stays within the free-tier limits for 500 users: one write per user per day and one read per report.

## Acceptance criteria
- [ ] AC-1 A valid record returns `204` and the fake store holds exactly one row with that `h`, the versions, and today's date as `first_seen` and `last_seen`.
- [ ] AC-2 A second record with the same `h` and new versions on a later (faked) day keeps `first_seen`, updates the versions and `last_seen`, and leaves one row.
- [ ] AC-3 Rejections: a record with an extra field, a long or non-hex `h`, a version such as `jane@abccorp.vn` or `1.0 beta`, a non-JSON body, an array, a 257-byte body, a `GET`, a `PUT`, a wrong content type, and an unknown path each give the status in requirement 2 and store nothing.
- [ ] AC-4 CORS: preflight from the allowed origin gets the headers of requirement 3; another origin, no origin and an unset `ALLOWED_ORIGIN` give `403`, store nothing, and send no `Access-Control-Allow-Origin` for the wrong origin.
- [ ] AC-5 Report: wrong, missing or unset token gives `403`; a right token returns counts that match the fake store for `days` of 1, 7 and 365; rows outside the window are excluded; out-of-range `days` gives `400`; `hashes=1` adds the list and without it no hash appears.
- [ ] AC-6 Privacy test: a request carrying an IP header, `User-Agent` and cookies leaves no trace in the store, the response, or any spied-on global (`console`, `fetch`).
- [ ] AC-7 A test of the D1 store with a minimal fake of the D1 API (`prepare`, `bind`, `run`, `all`) checks the exact SQL calls and that every value is bound as a parameter, never concatenated.
- [ ] AC-8 `npm run verify` passes; only `worker/heartbeat/**` changed; no new dependency; no domain, token or id in the repository.

## Edge cases
- Concurrent heartbeats of the same `h`: the upsert is atomic (`INSERT ... ON CONFLICT`).
- Client clock wrong: irrelevant, the date is the Worker's.
- Body with a UTF-8 BOM or a trailing newline: accepted if it is valid JSON within the size cap.
- `days` given twice or non-numeric: `400`.

## Out of scope
- The client call that sends the heartbeat (lead, CL-07/CL-08 runtime wiring); matching the report to the hashed target list and coverage metrics (CL-10); alerting; pruning old rows; deployment itself (the owner runs the runbook).
