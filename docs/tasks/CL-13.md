## Goal
Every repository the PO starts can use the same Antigravity tooling and the same two-agent workflow, from one versioned source, and can pick up changes without hand copying. Antigravity writes code in its own session on `ag/*` branches; Claude writes task cards and does QA; the PO merges (PO choice of 2026-11-05, option 1). This card builds the shared source and the way it reaches local and cloud sessions.

## Proposed layout of the source repository
Repository `antigravity-agent-toolkit`, private (PO answer to Q1, 2026-11-05; not created yet).

```
.claude-plugin/marketplace.json        marketplace: lists plugins/agy-bridge
plugins/agy-bridge/
  .claude-plugin/plugin.json
  hooks/hooks.json                     PreToolUse hook on Bash and PowerShell
  scripts/agy-guard.mjs, agy-job.mjs   from CL-11 and CL-12, policy-driven
  skills/antigravity-jobs/SKILL.md     how to write, start, watch and read a job
workflow/
  agents/                              brief writer, QA reviewer, delegation logger (generic)
  skills/                              routing rules (who does what), brief rules
  CLAUDE.snippet.md                    block merged between markers into CLAUDE.md
  templates/                           task card, CCR, PR template, QA checklist skeleton
tools/sync.mjs                         copies workflow/ into a repository and opens a PR
```

## Requirements
1. **Policy out of code.** The guard and the runner read `.claude/agy-policy.json` of the project (`CLAUDE_PROJECT_DIR`): `allowWrite`, `allowContext`, `deny`, `reviewOnly`, `promptDeny`. With no file, everything is denied. The Secure Mail Ring lists become that project's policy file.
2. **Runner unchanged in behaviour:** plan mode on every run, never skip-permissions, stream-json liveness, idle and hard limits, exit codes of CL-12. Paths resolve against the project directory, not the plugin directory.
3. **Hook** runs from `${CLAUDE_PLUGIN_ROOT}` and covers Bash and PowerShell; the allowed shell command forms are generalised to the plugin's runner path. The MCP tools stay refused.
4. **Sync tool:** `node tools/sync.mjs --target <repo> [--ref <tag>] [--open-pr]` copies the `workflow` files into `.claude/agents/`, `.claude/skills/` and `docs/templates/`, merges `CLAUDE.snippet.md` between marker comments, and writes `.claude/workflow.lock.json` (source, tag, file hashes). It refuses to overwrite a file whose hash differs from the lock unless `--force`. Opening a branch and a PR needs the explicit `--open-pr` flag; without it the tool only changes the working tree.
5. **Releases:** semantic tags; `claude plugin validate` in the checks; consumers follow the ref `stable`, which moves only after QA and PO approval (maker, checker, approver).
6. **Consumer set-up** documented: `extraKnownMarketplaces` and `enabledPlugins` in `.claude/settings.json`, a one-time `claude plugin install <name>@<marketplace> --scope project` where the docs require it, turning on auto-update in `/plugin`, and the sync command for the workflow content.
7. **Tests:** unit tests migrated from this repository (guard, runner) plus policy loading, sync (temporary directories: fresh copy, unchanged file, locally edited file, marker merge, lock file) and a check that the manifests validate.
8. **Secure Mail Ring migration** as a separate PR here after the source repository has a first tag: remove the local copies of the scripts and generic agents, add the policy file and the settings entries, update `AGENTS.md` ownership rows.
9. **Cloud check:** one throwaway cloud session confirms that the vendored `workflow` files are visible and that nothing depends on the plugin there.

## Acceptance criteria
- [ ] AC-1 Policy: tests show deny-by-default with no file, and the Secure Mail Ring policy reproduces today's decisions (the existing guard test cases pass unchanged against it).
- [ ] AC-2 Runner and guard: migrated CL-12 tests pass from the new location.
- [ ] AC-3 Sync: the five scenarios of requirement 7 pass; a dry run against this repository shows no changes after the migration PR.
- [ ] AC-4 Manifests: `claude plugin validate` passes for the marketplace and the plugin.
- [ ] AC-5 Install: on the PO's machine the plugin installs from the marketplace, `node` runs the runner through the skill's command, and a smoke job returns `OK`.
- [ ] AC-6 Update: a tagged change reaches the PO's machine through `claude plugin update`, and reaches a second repository through the sync PR.
- [ ] AC-7 Cloud: result of requirement 9 recorded.
- [ ] AC-8 Migration PR here is green (`npm run verify`) and shows only deletions of moved files plus the new settings and policy.

## Edge cases
- A consumer repository that edited a vendored file: the sync reports the conflict and stops for that file.
- `${CLAUDE_PLUGIN_ROOT}` changes on every plugin update, so no state is kept there; job data stays in the project's `.tools/agy-jobs/`.
- The shell-route check stays a heuristic (a command with the CLI name as the first word of a line is refused); the skill tells sessions to write such text with file tools.
- A plugin whose marketplace entry points at an external source is not installed from repository settings alone; the layout above uses a relative path so the marketplace copy carries the plugin.

## Out of scope
- Any write mode for Antigravity through the bridge, skip-permissions, or running agy in a container (test T8, separate card if the PO wants it).
- Running agy in cloud sessions.
- Publishing the repository publicly; organisation-level managed settings (personal plan).
- A public suffix list or other changes to `@smr/core`.
