## Goal
The pure decision engine behind the send-time guard exists and is correct on the plan's mandatory cases. Given a mail, a ring (or none), the rings on the device, the global settings and the history, `evaluate` returns every finding with its effective mode (Warn, Acknowledge or Block, with the global floor applied), the recipient reordering to apply, one verdict and a fingerprint that binds acknowledgements to the exact recipients and files. The import diff (`diffRings`), the ring suggestion for mails without a ring (E-3) and ring expiry (E-8) work too. After this card `createCore` has no stubbed function left except the share-code codec (CL-05B), and CL-08 can be written against the real engine.

## Design decisions (lead, reversible until Ready)
- **D1 Scope split.** The old CL-05 bundled eight modules. This card keeps the decision engine, which sits on the critical path (CL-08). The share-code codec, license check, import verification and heartbeat payload move to a new card **CL-05B**: they bring the first runtime dependency (`fflate`, needs an explicit "new dependency" line in its card), WebCrypto and build-time secrets, and are first needed by Stage 4/5/6. BOARD dependencies are updated accordingly (CL-08, AG-10, AG-11, AG-12).
- **D2 Clock.** `EvaluateInput` has no `now`, and the contract stays as is. `createCore({ fallback, now })` takes an optional `now: () => Date` (default `() => new Date()`). Expiry, the learning window and the look-alike reference set read it. Tests inject a fixed clock.
- **D3 Findings carry keys, not text.** Contract-v1 puts every user string behind `messageKey` + `params` (AGENTS §3, §6.5). The plan's "messages within the Smart Alerts length limit" is therefore the handler's job (CL-08: render with `t()`, one line per finding, truncate to the limit measured in Spike 7). Core guarantees stable, deterministic order: by kind in `POLICY_KEYS` order, then field (To, CC, BCC), then list order.
- **D4 Finding shapes** (subject, params), extending the contract fixtures:
  | kind | messageKey | subject | params |
  |---|---|---|---|
  | `outsider` | `finding.outsider` | address (display name if unresolved) | `address`, `field` (`TO`/`CC`/`BCC`) |
  | `missingToken` | `finding.missingToken` | file name | `file` |
  | `foreignRingToken` | `finding.foreignRingToken` | file name | `file`, `ring` (names of the foreign rings, joined by `, `) |
  | `lookalike` | `finding.lookalike` | address | `address`, `similarTo` (reference domain), `ring` (name of the ring the reference comes from, empty string for the sender's own domain) |
  | `firstTime` | `finding.firstTime` | address | `address` |
  | `fieldRule` | `finding.fieldRule.mustBeIn` / `mustNotBeIn` / `onlyIn` | address, or the pattern when `mustBeIn` finds nobody | `address` (or `pattern`), `field` (the field the rule names), plus `foundIn` when the match sits in another field |
  The fixtures show `ring: "Alpha"` for a ring named "Alpha – IA ABC Corp FY26"; core reports the full `ring.name`. The differential test (AC-8) compares everything except that value. AG-07 must write `finding.lookalike` so that an empty `ring` reads well; recorded on BOARD.
- **D5 Effective mode.** `mergePolicy` = per kind, the stricter of ring policy and global floor (as the stub does). The floor is applied at evaluation time and never written into the stored ring, so no import can lower it (T-1). Findings from `internalDomain: "warn"` (FR-1.7, reason `internal`) use mode Warn raised by the floor only, not the ring's `outsider` mode: the ring owner chose "warn" for colleagues. `STRICT_POLICY` (plan: outsider Acknowledge, foreignRingToken Block, lookalike Block, the rest Acknowledge) and `DEFAULT_POLICY` (all Warn) are exported for AG-03.
- **D6 Verdict.** The strictest mode among findings that are not satisfied: `block > acknowledge > warn > allow`. Only an `acknowledge` finding can be satisfied, by an entry of `input.acknowledged`. Warn is never satisfied (Outlook asks every time), Block never. All findings are returned, satisfied or not, so the acknowledge pane can show them ticked.
- **D7 Fingerprint and acknowledgement key.** `fingerprint` = hex SHA-256 over `JSON.stringify` of `{ v: 1, ring: id | null, recipients: sorted [field, normalised address or "?" + canonical display name], files: sorted canonical NFC names }`. Order inside a field does not matter (so the send-time reordering never invalidates an acknowledgement), the field does, the subject does not. Sorting is by code point, never `localeCompare`. `acknowledgementKey(fingerprint, finding)` = `"ak1:"` + first 32 hex of SHA-256 over fingerprint, kind, field and subject. Exported so that AG-09 stores and CL-08 verifies the same keys; the key is per finding, so a changed mail yields new keys and old ticks stop counting.
- **D8 Mail without a ring (D-05, FR-1.8, FR-6.5).** Ring checks that need a ring (missingToken, foreignRingToken, fieldRule, sorting) do not run. `outsider` runs against an empty ring with the sender's domain allowed: everyone outside the sender's domain and every unresolved recipient is reported. `lookalike` runs as in CL-04 (reference set = sender domain + non-expired rings). `firstTime` runs but only for recipients outside the sender's domain, to keep daily internal mail quiet (D-05 names friction as its risk). Modes come from `DEFAULT_POLICY` raised by the floor. `evaluate` never adopts a suggested ring by itself.
- **D9 Expired ring (E-8).** `isRingExpired(ring, now)` is true when `expiresAt` parses and lies before `now` (an unparseable date counts as not expired, as in CL-03/CL-04). A bound ring that has expired is evaluated as no ring (D8), so replying into an ended engagement raises the outsider warnings instead of silently accepting its old members. Expired rings are ignored by `suggestRing`.
- **D10 Ring suggestion (E-3).** Over non-expired rings, count the distinct resolved recipients outside the sender's domain that each ring covers (`createMemberIndex`). Return the ring with the highest count if it is at least 1 and unique; a tie or zero returns `null` (a wrong suggestion is worse than none). Internal-domain recipients neither help nor hurt.
- **D11 Diff.** `diffRings` compares members on their compiled normal form (case, punycode and trailing dots do not create a spurious add and remove), reports `revRelation` with the rules of FR-2.7, and every per-kind policy change with `loosened` (mode rank went down). Known gap, see Q4.

## Requirements
1. **`expiry`:** `isRingExpired(ring, now)`; `attachments.ts` and `lookalike.ts` use it instead of their private copies.
2. **`policy`:** `DEFAULT_POLICY`, `STRICT_POLICY`, `mergePolicy(ring, settings)` (public `CoreApi` method), `rankMode`, `stricter`.
3. **`fingerprint`:** `computeFingerprint(ring, snapshot)`, `acknowledgementKey(fingerprint, finding)` as in D7.
4. **`evaluate`:** `createEvaluate(now)` returning `evaluate(input)` as described in D3 to D9: findings from the CL-03/CL-04 detectors, `mutations` from `sortRecipients` (empty without ring), verdict, fingerprint. Never throws on any input that parses under the schemas; unresolved and malformed addresses are handled by the detectors.
5. **`diff`:** `diffRings(before, after)` per D11.
6. **`suggest`:** `suggestRing(rings, snapshot)` per D10. It needs the sender's domain, which `snapshot.from` provides.
7. **`createCore`:** `createCore({ fallback, now? })` replaces `evaluate`, `mergePolicy`, `diffRings`, `suggestRing`; only `encodeRing` and `decodeRing` still come from the fallback until CL-05B. `src/shared/contracts/core.ts` keeps `createCore({ fallback: stubCore })`.
8. **Performance (NFR-1):** `evaluate` on the CL-04 reference scenario (50 recipients, a 500-member ring plus three more, 20 attachments, full history) in best of five under 50 ms, skipped under Stryker as before.

## Acceptance criteria
- [ ] AC-1 Mode merging. `mergePolicy` is never below the ring and never below the floor, equals the ring when the floor is empty; a ring from an imported fixture cannot lower the floor (property + examples).
- [ ] AC-2 Plan examples. F1: ring `ALPHA` = {`abccorp.vn`, `kt@partner.vn`}, To `a@abccorp.vn`, CC `kt@partner.vn`, BCC `x@gmail.com` yields exactly one finding, `x@gmail.com (BCC)`. Strict preset yields outsider Acknowledge, foreignRingToken Block, lookalike Block, the other three Acknowledge.
- [ ] AC-3 Findings. One test per kind and per field-rule shape asserts kind, mode, messageKey, subject, field and params of D4; order is deterministic; `internalDomain: "warn"` recipients are Warn.
- [ ] AC-4 Verdict and acknowledgement. Block beats Acknowledge beats Warn; acknowledging every Acknowledge finding of a result lowers the verdict to Warn or allow but never below a Block or Warn finding; a key from another fingerprint or for a Block finding counts for nothing (property).
- [ ] AC-5 Fingerprint. Invariant under permutation inside a field and under applying the returned mutations; changes when any recipient, its field, any file name or the ring changes; stable across runs; no address appears in clear in the output.
- [ ] AC-6 No ring and expired ring. Mail without a ring reports external recipients, look-alikes and external first-time recipients and nothing else; an expired bound ring behaves identically; `evaluate` leaves a suggestion unused.
- [ ] AC-7 Ring suggestion. Unique best match, tie gives `null`, zero gives `null`, expired rings and internal recipients ignored.
- [ ] AC-8 Differential against contract fixtures. For the eight `evaluations.json` cases, real `evaluate` equals the fixture in verdict, finding kinds, modes, message keys, subjects, fields and parameter names (any fixture found wrong is corrected in the same PR and noted).
- [ ] AC-9 Diff. `revRelation` (new, newer, same, older), members compared in normal form, added and removed disjoint, `loosened` exactly when the rank drops; `diffRings(x, x)` is empty.
- [ ] AC-10 Wiring. `createCore` exposes the real functions with unchanged signatures; `contract.test.ts` untouched and green.
- [ ] AC-11 Quality gates. Line coverage ≥ 90 % on `packages/core` (target 100 %), mutation score ≥ 80 % on the new files, fast-check properties for verdict monotonicity, fingerprint invariance and no-throw; `package.json` and lockfile unchanged.
- [ ] AC-12 Performance. Best-of-five `evaluate` on the reference scenario under 50 ms.

## Edge cases
- Same address in two fields: two findings, two keys. Same address twice in one field: one finding per entry, one fingerprint element each.
- Recipients with display name only (unresolved): outsider finding, counted in the fingerprint by canonical display name.
- Ring with no tokens: no attachment findings. Attachment equal to an exempt extension or inline: no finding.
- Empty mail (no recipients, no files): verdict `allow`, valid fingerprint.
- Unparseable `expiresAt`, `learning.until` null, floor keys missing.
- A finding whose subject is 254 characters long still fits the schema.
