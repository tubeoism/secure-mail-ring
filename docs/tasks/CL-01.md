## Goal
Turn every **[Verify-S0]** item into a recorded fact on the real tenant and Outlook build, and give PO a Go/No-go for plan A (Web Add-in) or plan B (COM, plan §4.4) with evidence.

## Allowed paths
- `spikes/**` — throwaway harness (hello add-in, manifest, spike handlers). Never imported by product code.
- `docs/tasks/CL-01.md`, `docs/tasks/BOARD.md`
- `docs/tasks/evidence/CL-01/**` — PO screenshots, logs, environment table, results table.
- `docs/spikes/**` — runbook (one file per spike) and the Go/No-go summary.

## Inputs (read-only)
- Plan Stage 0 table and gate; §4.3 API mapping; §5.4 fail modes.

## Requirements
1. **Harness (Claude).** A minimal Outlook add-in in `spikes/`: XML manifest with `OnMessageSend` (`SoftBlock`), one compose button, one read-mode button; handlers instrumented to write a timestamped entry to `roamingSettings` (no email content). Served over HTTPS from a dev host (open question Q1).
2. **Runbook (Claude).** `docs/spikes/spike-N.md` for each spike: preconditions, exact PO steps, what to capture, pass/fail rule, and the plan decision it feeds. English, copy-paste-able.
3. **PO execution.** Day 1: tenant allows self-install (the Stage 0 stop-gate), then environment table, then Spikes 1–6, with Spike 7 running in parallel over 5 working days.
4. **Evidence review (Claude).** Record each result in `docs/spikes/RESULTS.md`, update plan assumptions through a plan v1.x change request (not by editing silently), and write the Go/No-go recommendation against the plan gate table.

## Spike scope

| # | Question answered | Pass rule (draft) |
|---|---|---|
| Day 1 | Can a user sideload a custom add-in on this tenant? | Add-in appears and runs; else stop and escalate (plan gate) |
| 1 | Does `OnMessageSend` fire on classic; `sendModeOverride` and `errorMessageMarkdown` behave; actual requirement sets | Dialog shown, block works, `isSetSupported` table filled. New Outlook is smoke only |
| 2 | Can `to/cc/bcc.setAsync` run inside `OnMessageSend`; display names kept; recipients re-resolved | Order change visible in sent item; else fall back to task-pane sorting |
| 3 | `roamingSettings` available in the JS-only runtime; real size after compression | Read/write works; max rings number recorded |
| 4 | Fail modes: offline, host 404, handler throws | Send is never blocked (invariant §8); table filled |
| 5 | Obfuscated bundle runs in the JS-only runtime | Safe obfuscator option list recorded |
| 6 | Acknowledge flow: `commandId` opens task pane from the dialog, `sessionData` survives, signal after Send Anyway (FR-7.5) | Flow works or fallback chosen |
| 7 | 5-day sideload stability incl. reboot, bundle update, manifest change + reinstall, Wef cache clear | At most one unexplained deactivation in 5 days (plan gate) |

## Acceptance criteria
- [x] AC-1 Runbook exists for Day 1 and Spikes 1–7, each with pass/fail rule and capture list.
- [x] AC-2 Harness builds and passes `npm run verify`; contains no email content logging.
- [ ] AC-3 `docs/spikes/RESULTS.md` has a filled row per spike with evidence links and a Go/No-go line.
- [ ] AC-4 Every **[Verify-S0]** tag in the plan is resolved or explicitly carried to a later stage with an owner.
- [ ] AC-5 Go/No-go recommendation matches the plan gate table and is signed off by PO.

## Edge cases
- Tenant blocks sideload → stop at Day 1; recommendation is IT/admin install or plan B (plan gate).
- Smart Alerts not firing after the Wef cache is cleared → counts as a Spike 7 deactivation.
- PO account policy changes during the 5 days → log it, restart the count.
